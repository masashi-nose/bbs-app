# GitHub Issue 作成

ユーザーの依頼や会話の文脈から issue の下書きを作り、確認を得てから `gh` CLI でこのリポジトリに issue を作成する。

issue は公開され、チームの誰かが後から読んで作業に着手するためのもの。会話の文脈を知らない人が読んでも、何が問題で何をすれば完了かが分かるように書く。

## 手順

### 1. 内容を集める

- ユーザーの依頼文と、会話中の関連情報（エラーメッセージ、レビュー指摘、議論の結論など）を集める。
- 関係するコードがあれば実際に読み、該当ファイルと行番号を特定する。推測で場所を書くと、読み手が誤った箇所を調べることになるため。
- 情報が足りず issue として成り立たない場合（例：「バグを issue にして」だけで、どのバグか分からない）は、作成前にユーザーに質問する。軽微な不足なら、分かる範囲で書いて「要確認」と明記すればよい。
- 依頼に複数の独立した問題が含まれていれば、1 issue 1 トピックに分割することを提案する。まとめると、完了の判断やクローズがしにくくなるため。

### 2. 種類を判定してテンプレートを選ぶ

| 種類 | 判定の目安 | ラベル | タイトル接頭辞 |
| --- | --- | --- | --- |
| バグ | 期待どおりに動かない、エラー、表示崩れ、セキュリティ上の欠陥 | `bug` | `[Bug]` |
| 機能追加・改善 | 新機能、既存機能の改善、パフォーマンス改善、リファクタリング | `enhancement` | `[Feature]` |
| ドキュメント | README・コメント・docs の追加や修正 | `documentation` | `[Docs]` |
| タスク・その他 | 上記以外の作業（環境構築、依存更新、調査など） | なし（必要なら既存ラベルから選ぶ） | `[Task]` |

ラベルは `gh label list` で確認できる既存のものだけを使う。存在しないラベルを指定すると `gh issue create` が失敗するため。アクセシビリティの問題なら `accessibility` も付けるなど、該当する既存ラベルは追加してよい。

テンプレートは `references/templates.md` を読んで使う。

### 3. 下書きを作ってユーザーに確認する

issue の作成は外部に公開される操作なので、必ず先に下書きを見せて承認を得る。次の形式で提示する：

```
以下の内容で issue を作成します。よろしいですか？

- リポジトリ: <owner/repo>
- タイトル: [Bug] ログイン失敗時にエラーメッセージが表示されない
- ラベル: bug
- 担当者: （指定があれば）

---
<本文>
---
```

- タイトルは、一覧で見て内容が分かる具体的な一文にする（「バグ修正」のような曖昧なものは避ける）。
- 本文は日本語で書く。コード・ファイル名・コマンド・エラーメッセージは原文のまま、バッククォートやコードブロックで囲む。
- 修正を求められたら反映して再提示する。

### 4. issue を作成する

承認を得たら作成する。本文は改行や記号を正しく渡すため、一時ファイル経由で `--body-file` を使う。

```bash
gh issue create \
  --title "<タイトル>" \
  --body-file <一時ファイルのパス> \
  --label "<ラベル>"
```

- 担当者の指定があれば `--assignee`（自分なら `@me`）を付ける。
- 複数のラベルは `--label` を繰り返す。
- 一時ファイルはスクラッチパッドなどプロジェクト外に置き、リポジトリに残さない。

### 5. 結果を報告する

作成された issue の URL・番号・タイトル・ラベルを報告する。複数作成した場合は一覧にする。

## 注意点

- `gh auth status` で未ログインなどのエラーが出た場合は、`gh auth login` の実行をユーザーに案内して止める。
- 似た issue がすでにある可能性があれば、`gh issue list --search "<キーワード>" --state all` で確認し、重複していればユーザーに伝える。
- 秘密情報（トークン、パスワード、`.env` の値、個人情報）は本文に含めない。ログを貼る場合も該当部分を伏せる。
